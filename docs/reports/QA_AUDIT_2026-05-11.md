## Bug Report

### CRITICAL Severity

#### BUG-001: All new user accounts created in production are permanently locked out
**File:** `/controllers/authController.js` line 133  
**Impact:** 100% of new user registrations fail to access the platform

**Root Cause:** The registration controller sets new accounts to `status: "pending"` in production environments where `EMAIL_HOST` is configured. The middleware blocks all API access for pending accounts with a 403 response. The email verification link system then calls an endpoint that activates the account — but if email delivery fails, or the link expires, the user is permanently locked out with no recovery path from the UI.

```javascript
// authController.js line 133
status: (isDevelopment || !process.env.EMAIL_HOST) ? 'active' : 'pending'
```

**Evidence:** The `api.js` interceptor handles 403 with `Account is not active` by redirecting to `/login?error=verify-email`. After verifying email, users must manually log in. This flow is broken if the verification email is not received.

**Fix Required:** 
- Add a "Resend verification email" link to the login page when the error is `verify-email`
- Add an admin endpoint to manually activate accounts
- Add a `/verify-email` page that handles token expiry gracefully

---

#### BUG-002: Next.js Edge Middleware checks cookie for auth but client only sets localStorage
**File:** `/client/middleware.js`, `/client/lib/authService.js`  
**Impact:** Any user whose browser session cookie expires is permanently redirected to /login even with a valid localStorage token

**Root Cause:** The Next.js Edge Middleware (which runs server-side before React renders) checks for a `token` COOKIE:
```javascript
const sessionCookie =
  request.cookies.get(SESSION_COOKIE)?.value ||
  request.cookies.get('token')?.value;
```

However, `authService.login()` only sets a localStorage token — it does NOT set a cookie. This means:
1. After a hard browser session reset (tab close, incognito), the cookie is gone
2. The middleware redirects to `/login` even though `localStorage.getItem('token')` has a valid token
3. This causes a jarring experience where users must log in again even on fresh page loads

**Evidence:** All E2E tests that attempted to mock auth by setting only localStorage failed. Tests only passed after adding `context.addCookies([{ name: 'token', ... }])`.

**Fix Required:** The `authService.login()` and `setUserFromOAuth()` functions must set a cookie in addition to localStorage. The cookie should be set via a `Set-Cookie` response header from the backend `/auth/login` endpoint, or by `document.cookie` in the client.

### HIGH Severity

#### BUG-003: Inconsistent HTTP status codes from auth middleware (500 vs 401/403)
**File:** `/middleware/authMiddleware.js` line 226  
**Impact:** Some failed auth requests return 500 instead of 401, breaking client-side retry logic

**Root Cause:** The `authenticateToken` middleware has a catch-all `catch` block that returns `500 { message: "Authentication error" }` for unhandled exceptions. If the JWT library throws (e.g., malformed token), this returns 500 instead of 401. The axios interceptor in `api.js` only retries on 401, so a 500 from auth failure breaks the refresh-and-retry flow.

**Fix Required:** Replace the generic 500 catch with specific JWT error handling that returns 401 for all token validation failures.

---

#### BUG-004: Rate limiter active during E2E tests despite DISABLE_RATE_LIMIT env var
**File:** `/config/playwright.config.js`, rate limiting middleware  
**Impact:** API contract tests receive 429 instead of expected 401 for unauthenticated requests

**Root Cause:** The Playwright config sets `DISABLE_RATE_LIMIT: 'true'` in the `webServer.env` block, but this env var is only applied when Playwright starts the server itself (when `reuseExistingServer: false`). In local development where `reuseExistingServer: true` is used (existing server detected), the rate limiter is active.

The smoke tests were updated to accept both `[401, 429]` to work around this. However, it means the API contract tests cannot verify the exact status code when running locally against a pre-started server.

**Fix Required:** The rate limiter should check `process.env.DISABLE_RATE_LIMIT` at request time, not just at startup. Alternatively, reset the rate limit window between test suites.

### MEDIUM Severity

#### BUG-007: `performLogout()` in AuthContext has token cleanup race condition
**File:** `/client/lib/AuthContext.jsx` lines 134-146  
**Impact:** If the server logout call succeeds but then `localStorage.removeItem` is called in the `catch` block (which won't execute on success), tokens may persist in localStorage after logout

**Root Cause:** The `performLogout()` function calls `authService.logout()` and only clears localStorage in the `catch` block:
```javascript
const performLogout = useCallback(async () => {
  try {
    await authService.logout();
  } catch {
    localStorage.removeItem('token');  // only runs on error
    ...
  }
  localStorage.removeItem(PROFILE_KEY);  // this runs always
  setUser(null);
```

If `authService.logout()` succeeds (200 response), the `catch` block is skipped, so `token` and `refreshToken` are NOT removed from localStorage. Only `PROFILE_KEY` is removed. The server-side session is invalidated but the client still has a token.

**Fix Required:** Move `localStorage.removeItem('token')` and `localStorage.removeItem('refreshToken')` outside the catch block so they always execute.

## Architecture Issues Discovered

### AUTH-001: Dual authentication layers with different mechanisms
**Severity:** Design Concern  

The application has two authentication layers that use different storage mechanisms:
- **Layer 1 (Server-side):** Next.js Edge Middleware reads from **cookies** to block unauthenticated requests before React renders
- **Layer 2 (Client-side):** `AuthContext.restoreSession()` reads from **localStorage**, calls `/auth/me`, sets React `user` state
- **Layer 3 (API):** Axios interceptor reads from **localStorage** to set `Authorization: Bearer` header

For authentication to work correctly, ALL THREE layers must be populated. Currently, only the client-side layers (2 and 3) are automatically populated on login. Layer 1 (cookie) is only set if the browser receives a `Set-Cookie` header from the backend, which the current login endpoint does not send.

**Recommendation:** Add `Set-Cookie: token=<jwt>; HttpOnly; SameSite=Strict; Path=/` to the `/auth/login` response. The middleware should preferably use an HttpOnly cookie for security (preventing XSS token theft).

---

### AUTH-002: JWT stored in localStorage is vulnerable to XSS
**Severity:** Security Concern  

Storing the JWT in `localStorage` (as done by `authService.login()`) is vulnerable to cross-site scripting (XSS) attacks. Any injected script can read `localStorage.getItem('token')` and exfiltrate the token.

**Recommendation:** Migrate to HttpOnly cookies for token storage. The current cookie-based middleware check is a partial implementation of this pattern.

## Performance Observations

- **Landing page load:** 862ms to 1.1s (acceptable)
- **Dashboard pages with mocked APIs:** 875ms to 3.4s (the longer times are page compilation on first access in dev mode)
- **Auth flow (login → dashboard):** ~11.7s with real backend (too slow; indicates restoreSession() adds latency on each navigation)

**Recommendation:** The `restoreSession()` call makes a synchronous network request on every app mount. Consider caching the user state in a session cookie that the middleware can validate without an API round-trip.
